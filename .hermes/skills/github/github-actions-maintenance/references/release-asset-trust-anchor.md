# Release-asset trust anchors (in-tree SHA256SUMS)

When a plugin/provider ships a binary by downloading it from GitHub Releases,
the checksum anchor must come from the BUILD, not from the release itself: a
release's own SHA256SUMS file is self-authenticating (same publisher as the
artifact), so a re-published or tampered release can carry matching self-signed
sums. The pinned plugin tree is the non-editable anchor.

## The pattern (validated on two PlayForm repos)

1. Build.yml's per-target matrix already emits `SHA256SUMS-<target>.txt` for
   every artifact and attaches it to the release.
2. Build.yml Finalize job (runs once, after the whole matrix): downloads the
   per-target sums assets (`gh release download --pattern "SHA256SUMS-<target>.txt"`),
   consolidates them into `<child-submodule>/SHA256SUMS.txt` with header
   `BINARY_VERSION: <ver>`, a `# GENERATED BY Build.yml - do not edit by hand.`
   line, and one block per target (`<target>:` then the sums lines indented two
   spaces), then commits INSIDE the child submodule on its Current branch and
   pushes. Skip the commit when nothing changed.
3. Publish.yml gains a Bump-Plugin-Gitlink job (runs after the last publish
   job, tag-gated): fetch the child's Current with a bounded retry loop (the
   Finalize child push races this job), checkout origin/Current, commit the
   parent gitlink bump (bot identity github-actions[bot]), push HEAD to the
   parent's branch.
4. The downloader (download.sh) validates in this order:
    - in-tree `SHA256SUMS.txt` — used only when its BINARY_VERSION header
      matches the version being installed (a pinned tree never silently
      validates an older release); extract the `<target>:` block as the sums
      input (no network needed).
    - else the release's per-target `SHA256SUMS-<target>.txt`.
    - else a loud WARNING and skip checksum verification (releases cut before
      the anchor existed stay installable).
    - Any mismatch when a checksum IS available: hard error, refuse to
      install. Warn-not-fail applies ONLY to an absent sums source, never to
      a mismatch.

## Why in-tree and not release-only

- Self-authentication: the tree's checksum file is committed by CI, not
  hand-maintained, so it is a trustworthy non-editable source.
- The catalog-review rule that a plugin's register() never writes into its
  own directory makes in-tree binary SHIPPING impossible — download-and-
  validate is the only compliant model, and the checksum file is the smallest
  non-executable thing the tree can pin.

## Adaptation notes when porting to a new repo

- Tag prefix differs per repo (e.g. Aphrodite/v vs Cloudflare/v) — strip the
  repo's own prefix, never a remembered one, and read the prefix from the
  workflow's tag trigger.
- The target list differs (a repo with no Windows leg adjusts the target
  loop and the child path).
- Keep the repo's action-pinning style (SHA + `# tag` comment) in the new
  steps; do not unpin actions while adding workflow steps.
- The child submodule may be at a different commit than the parent's gitlink
  (local checkout ahead) — the Bump job normalizes this on the next release;
  locally, bump the gitlink to the child's actual tip so `git submodule
status` shows no `+`.
