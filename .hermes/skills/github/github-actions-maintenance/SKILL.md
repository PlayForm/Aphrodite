# GitHub Actions Maintenance

In workflow generation systems there are two directories:

- `./Workflow/` - **Source of truth.** Template files with `$Branch$` placeholders and `uses:` references.
- `./.github/workflows/` - **Generated output.** Produced by running the workflow command. **Never read this directory to populate build-time env vars.**

## Procedure

### 1. Pin actions to commit SHAs

Run `./Update.sh` to convert floating tags (`@v7.0.1`) to immutable commit SHAs
(`@3d3c42e # v7.0.1`).

The script:

- Finds all `uses:` references in workflow files
- Resolves the latest semver tag via `gh api repos/{repo}/tags`
- Dereferences annotated tags to commit SHAs
- Writes `action@sha # tag` format

### 2. Verify pinned versions

For each pinned action, verify the SHA matches the latest release:

```bash
curl -s https://api.github.com/repos/{owner}/{repo}/releases/latest | jq -r '.tag_name, .published_at'
curl -s "https://api.github.com/repos/{owner}/{repo}/tags?per_page=20" | jq -r '.[] | "\(.name)\t\(.commit.sha)"'
```

Some repos (like `github/codeql-action`) have separate "bundle" releases vs. "action"
tags. Track the action tag, not the bundle.

### 3. Sync templates to generated files

Run the workflow command (e.g., `Maintain Workflow`) to regenerate
`./.github/workflows/` from `./Workflow/` templates.

### 4. Versions-only updates in pre-existing repos (`Maintain Workflow --Review` / `--Absorb`)

When a repo's workflows are customized (not straight template copies) and only the
action versions drift, do NOT regenerate - that replaces whole files. Use the
versions-only pair, both run from the target repo root (cwd-based, repository-agnostic):

- **`Maintain Workflow --Review`** - read-only: lists every `uses:` action under
  `.github/`, its current ref, the latest tag/SHA from `gh api`, and what the
  `Workflow/` templates would apply. Writes nothing (no `Update.sh`, no mkdir);
  degrades gracefully when `.github/` is absent. Statuses: CURRENT / STALE /
  FLOATING (unpinned tag, e.g. `@v1`) / UNKNOWN (API failure - degrade, don't crash).
- **`Maintain Workflow --Absorb`** - two-phase, versions only:
    - Phase 1 (no absorb-marked `Update.sh` in the repo root): writes a scoped
      `Update.sh` that pins only `.github/` YAML `uses:` refs (same logic as the
      canonical `Update.sh`, plus an action manifest and a verification footer;
      marker line `# Generated by Maintain Workflow --Absorb`). Run it.
    - Phase 2 (`Update.sh` present): reconciles against the `Workflow/` templates
      in place - replaces only the version segment, never downgrades (repo pin kept
      when its tag is newer than the template's), leaves template-uncovered actions
      at the `Update.sh` pin.
    - An `Update.sh` present WITHOUT the absorb marker → refuse to overwrite.
    - Acceptance: `git diff` on `.github/` shows ONLY `uses:` lines - no structure
      changes, no dropped lines; files without trailing newlines stay byte-preserved.

### Rebuilding the Maintain library

`sh Source/prepublishOnly.sh` (sources `Fetch.sh` first, so the `Workflow/`
templates must exist and carry pins; the `Build` CLI is a separate npm package).
The `Build` helper CATCHES tsc errors and still exits 0 - grep the build log for
`error TS` to see real failures. A `Cannot find module '…/pnpm/global/store/…/typescript/bin/tsc'`
failure means the global pnpm typescript link is corrupt (dir exists, package content
incomplete) - repair with `pnpm add -g typescript@<version>` matching the linked
version, then re-run the build.

## Aphrodite CI facts

- `Build.yml` runs a 4-target build matrix and produces 12 release assets
  (per-target checksums consolidated in the Finalize job - see
  `references/release-asset-trust-anchor.md`).
- `Publish.yml` is a cargo publish chain: `headroom-core` → `aphrodite` →
  `aphrodite-hermes`, triggered by tags named `Aphrodite/v*`.
- Workflow changes land on the `Development` branch (the repo default); a pin
  in `.github/workflows/` must resolve to the same SHA CI actually runs.

## Selective workflow enablement after org-wide Actions lockdown

To run ONLY one workflow (e.g. the Dependabot auto-approve) after `PUT /orgs/{org}/actions/permissions -F enabled_repositories=none`:

- **Org level has NO workflow granularity** - only `all` / `none` / `selected` repos. There is no org-scope workflow allowlist and no API for one (`enabled_workflows` appears nowhere in the REST OpenAPI; the UI "only enable specific workflows" option is per-repo and Enterprise-only).
- **Free-plan recipe per repo**: 1) `PUT /orgs/{org}/actions/permissions -F enabled_repositories=selected -F allowed_actions=all`; 2) `PUT /orgs/{org}/actions/permissions/repositories/{repo_id}` (id via `repos/{o}/{r}` `.id`); 3) `PUT /repos/{o}/{r}/actions/permissions -F enabled=true -F allowed_actions=all` (`-F` typed boolean - `-f` sends string and 422s); 4) `GET .../actions/workflows --paginate` then `PUT /repos/{o}/{r}/actions/workflows/{id}/disable` for every file except the keeper. Per-workflow disable/enable IS public API on all plans; retry once - a disable can transiently fail.
- **Count workflow-disable failures explicitly** - an apply loop that logs `DISABLE-FAIL` to a file but only sums repo-level failures silently misses stragglers; verify by read-back listing each workflow's `state` (`active` vs `disabled_manually`).
- **Dynamic pseudo-workflows in the workflows list are NOT workflow files**: `dynamic/dependabot/dependabot-updates` and `dynamic/dependabot/update-graph` are Dependabot itself (keep active - disabling kills the updates); `dynamic/github-code-scanning/codeql` cannot be disabled via the workflows API and is inert unless GHAS is on (`GET .../code-scanning/default-setup` returns 403 "Advanced Security must be enabled" on free-plan private repos; the endpoint is PATCH, not PUT).
- **Archived orgs accept these Actions-permissions endpoints** (org PUT, repo add-selected, repo enable all succeed) even though repo content ops 404 there.

## Dependabot auto-merge failures and branch protection

`gh pr merge --auto` (the Dependabot auto-accept pattern) fails with `GraphQL: Pull request Protected branch rules not configured for this branch (enablePullRequestAutoMerge)` when the base branch has NO branch protection rules requiring at least one status check or review - GitHub refuses `enablePullRequestAutoMerge` without them.

Why it "always worked" until it didn't: gh CLI only calls `enablePullRequestAutoMerge` when the PR is NOT immediately mergeable. MergeStateStatus CLEAN/UNSTABLE/HAS_HOOKS merge directly (silent, no protection needed); BEHIND/BLOCKED take the auto-merge path. In a multi-PR dependabot batch, the 1st PR merges while immediately mergeable; each later PR is then BEHIND (base moved) and hits the auto-merge path - which then requires branch protection. Single-PR batches never hit it. So a workflow that succeeded for weeks fails only on the 2nd/3rd PR of a batch.

### Enabling protection across many repos/orgs

- **Never require a status-check context that doesn't run on that repo** - a phantom context never passes, so every PR is permanently unmergeable. Per-repo rule: if `.github/workflows/GitHub.yml` exists on the default branch → require `Assign`; otherwise → require 1 approving review (same auto-merge precondition, no phantom check).
- **Protection alone is not enough** - the repo must also have `allow_auto_merge=true` (PATCH `repos/{o}/{r}`).
- **Never clobber existing protection**: GET `branches/{b}/protection` first, skip repos that already have it.
- **Send the protection body as a JSON file via `--input`** - `gh api -f` stringifies booleans/ints and `-F`/`-f` mixes still 422 on nested objects like `required_pull_request_reviews`; a JSON file avoids both.
- **Batch 100+ repos as a background script** with `notify_on_complete=true`, logging each repo as applied/skipped/failed; reconcile the enumeration count (per-org sums vs total file lines - API output truncation is silent and leaves stragglers).

## Pitfalls

- **Never read generated files to populate env vars used to generate them.** `Fetch.sh`
  (or equivalent) must only grep `./Workflow/`, never `./.github/workflows/`. Reading
  generated output creates a feedback loop: env vars come back `undefined` → generated
  files get `# undefined` baked in → the next extraction reads `# undefined` as
  source-of-truth. Remove `$Root/.github/workflows/` from grep commands in version
  extraction functions.
- **Handle annotated AND lightweight tags.** For a lightweight tag, `ref.object.sha` is
  the commit directly; for an annotated tag it is the tag object and must be dereferenced
  via `git/tags/{sha}` to reach the commit. `Update.sh` does both - keep it that way.
- **Decide tag-vs-release tracking and stay consistent.** Some repos (e.g.
  `actions-rs/cargo`, `actions-rs/toolchain`) have tags newer than their latest GitHub
  Release. `Update.sh` tracks the highest semver tag; `/releases/latest` tracks the
  release. Both are valid - document the choice and apply it uniformly.
- **`Maintain Workflow`'s resolver can lag the file's current tag.** Observed: a
  workflow already on `pnpm/action-setup@v6.0.10` came back SHA-pinned as
  `# v6.0.9` after regeneration. After any regen/update run, diff the `uses:`
  annotations - a pin that regressed to an older tag means the resolver's
  known-good SHA predates the file; re-check the intended tag's SHA before
  committing.
- **macOS BSD sed has no `\s`.** `/usr/bin/sed -E` (BSD) does not implement GNU `\s`,
  so `s|(uses:\s+)…|` never matches: the script logs "Updated" and rewrites every
  file byte-identical while claiming success. Write `[[:space:]]` instead.
- **Verify a claimed update actually landed.** A "New action part" log line does not
  mean the rewrite fired - grep the file for the new pin after running `Update.sh`/
  absorb (the BSD-sed case above rewrote files unchanged while logging success).
- **`while read` drops an unterminated final line.** `while IFS= read -r line; do …
done < file` never enters the body for the last line when the file has no trailing
  newline (read exits non-zero at EOF), so rewrites silently delete it. Preserve
  byte-fidelity with `while IFS= read -r line || { Newline=0; [ -n "$line" ]; }; do`
  plus a conditional `printf '\n'`; the `[ -n "$line" ]` guard stops the loop at
  EOF-empty (read empties the variable) - `|| Newline=0` alone would loop forever.
