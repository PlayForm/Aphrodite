# PlayForm Cargo Maintenance (Aphrodite)

Version cycle and release mechanics for the Aphrodite Rust workspace:
`crates/aphrodite` (core), `crates/aphrodite-hermes` (plugin binary), and the
vendored fork `vendor/headroom` (`aphrodite-headroom-core`). The repo lives in
the PlayForm/Aphrodite monorepo, branch `Development` (public line) / `Current`,
remote `Source`. Release ceremony and gates are owned by
`aphrodite-release-workflow`; this skill owns the bump → rebuild → retest cycle
and the crates.io publish mechanics for the workspace crates.

## When to Use

- "bump the version", "minor/major/patch bump", "rebuild and retest"
- Wiring or checking crates.io publishing for the Aphrodite crates

## Procedure (bump -> rebuild -> retest)

1. **Bump in the lockstep set** (repo convention - all must move together):
    - `crates/aphrodite/Cargo.toml` -> `version = "X.Y.Z"` (`build.rs` stamps it
      into the binary)
    - `crates/aphrodite-hermes/Cargo.toml` -> `version = "X.Y.Z"` AND its
      `aphrodite = { path = "../aphrodite", version = "X", ... }` dep pin (must
      equal the crates.io version or `cargo publish` fails)
    - `package.json` -> `version` (carries the binary version)
    - `CHANGELOG.md` -> new `## X.Y.Z` entry at the top with `### Change` /
      `- Bumped package version from A.B.C to X.Y.Z.`
    - `README.md` -> the release badge `message=vX.Y.Z` (badge labels must stay
      truthful; the help-text block is version-free and needs no edit)
    - Generate the CHANGELOG entry from git history:
      `git log <last-tag>..HEAD` plus `git -C vendor/headroom log` when the
      fork moved. Distill the sections into the entry; verify the change set
      against the diff before writing.
    - In the multi-crate workspace the lockstep set also includes: the plugin
      submodule's `plugin.yaml` + `BINARY_VERSION`, version fixtures
      (`fixtures/<crate>_version.json`), and README badges in BOTH repos (root +
      plugin submodule). Grep the tree for the old version after editing and
      classify each hit: version-of-record moves, INCLUDING workflow comments
      that name the dep-pin version (e.g. Publish.yml prose describing the
      path-dep) - left stale they describe a pin that no longer exists;
      contracts (`minimum_hermes_plugin_version`), historical CHANGELOG
      entries and generated docs (regenerated by CI to scratch, not diffed)
      do NOT move.
2. **Rebuild**: `cargo build --release` - the binary only reports the new
   version after a rebuild (build.rs re-stamps at build time, not on edit).
3. **Refresh installed binaries**: `cargo install --path crates/<name>
--force` - the standing convention is that locally developed packages stay
   installed from their local dev checkout, never replaced by crates.io
   versions. The workspace root Cargo.toml is a virtual manifest, so point at
   the crate dir (`cargo install --path crates/aphrodite --force`). When the
   plugin locates the binary at a managed path, refresh THAT copy too. When
   the repo ships a plugin that must stay byte-consistent with the binary,
   re-sync the WHOLE installed plugin tree, not just the binary:
   `rsync -a --exclude='.git' --exclude='__pycache__' plugins/aphrodite/
~/.hermes/plugins/aphrodite/` - copying only the binaries leaves the
   installed copy's `BINARY_VERSION` / `plugin.yaml` stale, and the version
   handshake then reports binary X vs installed pin Y. Verify all four agree
   afterwards: `aphrodite --version`, the dylib version report, `plugin.yaml`
   `version`, and `BINARY_VERSION`.
4. **Retest** with machine-checkable exits: `./target/release/aphrodite
--version` AND the installed `aphrodite --version` must both print the new
   version; a live run must exit 0 and its newest window header must now read
   `from <previous-tag> to last commit`. The tool's own output is the proof.
5. **Re-check git state**: an external sync often COMMITS the bump locally
   (working tree goes clean while `git log` gains a commit). Verify
   `git show HEAD:<file>` carries the new version before claiming anything was
   lost, kept, or published.

## Release execution (only after the publish gate is explicitly lifted)

1. Commit + push the PLUGIN submodule FIRST (its post-commit hook bumps the
   parent gitlink), then stage everything in the parent and push - verify
   `git submodule status` shows no `+` before tagging.
2. Annotated tag `Aphrodite/v<version>` on the parent + push. The tag format
   is ALWAYS `Aphrodite/v<semver>` (annotated; never deviate) - the workflows
   key off `startsWith(github.ref, 'refs/tags/Aphrodite/')`, and the tag must
   exist in that exact form or the release jobs never run. This triggers
   Build.yml (GitHub release with per-target assets) AND Publish.yml's
   tag-reachable `cargo publish` for `aphrodite` + `aphrodite-hermes` -
   re-verify the trigger table at the tag commit (Gate R7 in
   `aphrodite-release-workflow`); the headroom fork publish is
   `workflow_dispatch`-gated only.
3. When the headroom fork version moved, dispatch its publish explicitly
   BEFORE the parent tag push:
   `gh workflow run Publish.yml -f publish_crates=true --ref Current`, then
   watch both runs with `gh run watch <id> --exit-status` (background +
   notify_on_complete; never poll in a loop).
4. Verify EXTERNALLY, never from the workflow's green check alone:
    - crates.io: `curl -s -H "User-Agent: <contact>"
https://crates.io/api/v1/crates/<name>` -> `max_version` equals the new
      version (UA-less requests get dropped).
    - Release assets: `gh release view <tag> --json assets --jq '.assets[].name'`
      -> expected per-target binary + dylib + checksum set (12 assets).
5. Re-dispatches are idempotent: the workflow's index-version skip
   (`already_published`) makes a rerun after a partial failure safe.

## Publish gate (USER RULE)

- A version bump is NEVER authorization to publish. "don't re-publish" is a
  standing gate: no `cargo publish`, no tag push, no push, no release - until
  explicitly instructed. Local commits by the sync are fine; remote-facing
  actions are not.
- Publishing from GitHub is NOT uniform across the fleet: PlayForm/Aphrodite's
  Publish.yml publishes `aphrodite` + `aphrodite-hermes` on `Aphrodite/v*`
  tag push with `CARGO_REGISTRY_TOKEN`; crates gated to crates.io TRUSTED
  PUBLISHING (OIDC) reject API tokens with a 403. Check the target repo's
  `.github/workflows/` AND the crate's crates.io Trusted Publishing settings
  before assuming either way. Pattern details:
  `references/publish-from-github.md`.

## Pitfalls

- **A workspace crate whose manifest carries `version = "X.Y.Z"` TWICE -
  the crate's own version AND a path-dep pin (`crate = { path = "../crate",
version = "X.Y.Z", ... }`) - a bare-string patch on `version = "X.Y.Z"`
  hits the FIRST occurrence (the dep pin) and silently leaves the crate
  version stale.** `cargo build` still succeeds (the dep pin matches the
  path crate's current version), so the drift is invisible until
  `--version` reports the old number or `cargo publish` fails. Match each
  occurrence with surrounding context (`name = "<crate>"\nversion = ...`
  for the crate version; the `path = "../..."` line for the pin), then
  `grep -c 'version = "X.Y.Z"' <file>` and confirm it returns the expected
  count (2 for a crate with a path-dep pin, 1 otherwise) before building.
- **A CI "already published" check is a silent-skip trap, not a safety
  gate.** A publish workflow that skips when the index already serves the
  manifest version goes GREEN and publishes NOTHING while the content
  advanced - a fork/submodule whose tree moved past the last published
  commit ships stale on crates.io with zero red anywhere. Before claiming a
  release, compare the fork's content delta since the LAST PUBLISHED COMMIT
  (`git log <last-published-commit>..HEAD` inside the fork/submodule), not
  just the version string; if content moved, bump the crate version FIRST -
  a live version in the index means the next dispatch skips.
- **A parent crate whose `path + version` dep pins a fork crate needs the
  fork version LIVE on the registry before ANY publish path runs** - `cargo
publish` strips the `path` key and the registry resolves the pinned
  version at publish time, so the fork crate must be published first (in
  the workflow's `needs:` chain) AND before a tag push that auto-publishes
  the parent. Sequence: fork bump → fork tag → fork publish (dispatch) →
  parent tag. Publishing the parent first fails on the missing dependency
  version; re-publishing after a successful earlier publish errors red
  ("already published") - both are known, plan around them.
- A number already on crates.io can never be claimed again: before
  committing fixes on top of a released line, check `max_version` with
  the UA'd curl (`curl -s -H "User-Agent: <contact>"
https://crates.io/api/v1/crates/<name>`; UA-less requests are dropped)
  and bump to the next patch FIRST if the working-tree version already
  equals it - otherwise the commit claims a published number and the
  next publish fails.
- **CI-only deltas after a tag do NOT warrant a bump: workflow YAML fixes
  and gitlink-pointer updates riding `Current` leave the published
  artifacts byte-identical, so re-releasing burns a version number on
  nothing.** Audit with `git diff --stat <tag>..HEAD` plus
  `git diff --name-only <tag>..HEAD` - when every changed path is under
  `.github/` (plus the submodule gitlink), the release stands and the
  workflow fixes ride along automatically on the NEXT tag. Bump only when
  crate/plugin SOURCE content moved.
- crates.io renders the PACKAGE-dir README (cargo auto-includes
  `crates/<name>/README.md`, not the root README). Relative links
  (`](docs/...)`) render as `blob/HEAD` on the crates.io page - make
  every link an absolute `tree/Development` URL in ALL package READMEs of a
  workspace; fixing only the root README leaves the crates.io pages
  broken.
- Version POINTERS on the distributed line (`BINARY_VERSION`, download
  pins) advance LAST, only after the release they point at exists.
  A pointer is a live distribution link - bumping it early makes
  consumers fetch a not-yet-published artifact and error. The parent
  release tags first; the pointer bump + gitlink float is the final
  step.
- The sync that commits your bump may also fast-forward/force-reset the branch
  mid-task - re-run `git log` + `git show HEAD:<file>` immediately before any
  git-level claim; `git status` alone is not enough.
- Version claims must be verified in the BUILT binary's output (`--version`),
  not just the source files - a stale binary reports the old version after a
  source-only bump.
- When the bump touches README content, apply the `github-readme-generation`
  restyle checklist (badges, em-quads, GFM alerts, byte-exact examples).
- A failed release run that was fixed in the workflow file needs the TAG
  moved to the fixed commit (`git tag -f` + `git push --force Source <tag>`) -
  the workflow that runs is the one at the tag's commit, so pushing the branch
  alone does not re-trigger the tag-push workflow.
- **A job that WRITES INTO a submodule needs its own `actions/checkout` with
  `submodules: recursive`** - a release job that previously only hit the
  network (asset verification, release notes) has no checkout, and adding a
  step that writes `plugins/aphrodite/SHA256SUMS.txt` fails with "No such file
  or directory" at the first redirect. The v0.0.3 Build.yml Finalize job
  failed exactly this way (matrix + release assets fine, Finalize red); the
  fix is a checkout step (submodules + fetch-depth 0) at the top of the job.
  When the release already exists, do NOT move the tag to re-run - complete
  the missing artifact manually (assemble the in-tree checksum file from the
  release's per-target sums with the BINARY_VERSION header, commit + push it
  in the child, bump the parent gitlink) and let the workflow fix ride for
  future releases.
- **Cross-repo child pushes from a workflow need a PAT, AND the persisted
  GITHUB_TOKEN extraheader must be removed GLOBALLY (or overridden
  per-command) or the push silently 403s as `github-actions[bot]` even with
  a valid PAT in the URL.** actions/checkout sets
  `http.https://github.com/.extraheader` in the GLOBAL config; a child-local
  `git config --unset-all` does not reach it. Working recipe: store a
  fine-grained PAT (contents:write on the CHILD repo only) as a secret on the
  Release ENVIRONMENT (`gh secret set NAME --env Release`; the job needs
  `environment: Release`), then:
  `git -C "$CHILD" config --global --unset-all http.https://github.com/.extraheader || true`
  followed by
  `git -C "$CHILD" -c http.https://github.com/.extraheader= push "https://x-access-token:${PAT}...git" Current`.
- **A gitlink-bump job that runs on the tag push RACES the release workflow's
  Finalize child push - the Bump job must WAIT for the child tip whose
  in-tree SHA256SUMS.txt pins the release version, not just fetch once.**
  The Publish workflow starts the same instant as the Build matrix; its
  Bump job completes minutes before Finalize pushes the checksum commit, so
  it always sees the pre-checksum child tip and exits "nothing to bump",
  leaving the parent gitlink stale by one child commit after every release.
  Fixed loop: fetch origin Current, then
  `git show origin/Current:SHA256SUMS.txt | grep -q "^BINARY_VERSION: ${V}$"`
  (bounded, e.g. 40 x 15s), error out if it never appears. A 5x10s fetch
  retry is NOT enough - it only rides out a transient fetch failure.
- **A workflow job that PUSHES into a submodule's own repo cannot use
  `GITHUB_TOKEN` - it is scoped to the parent repo and 403s on any other
  repo (public or private).** The Finalize job that commits the in-tree
  `SHA256SUMS.txt` inside the child checkout must push to `<owner>/<child>`,
  so it needs a fine-grained PAT scoped to the CHILD repo only (Contents:
  write). Store it as an ENVIRONMENT secret
  (`gh secret set <NAME> --env <Env>` - repo-wide is unnecessary exposure),
  declare `environment: <Env>` on the job (environment secrets reach only
  jobs that declare the environment), and push via the token URL:
  `git -C "$CHILD" push "https://x-access-token:${PAT}...git" Current`.
  Guard the step with a loud `::error::` + exit 1 when the secret is empty
    - never push an unauth'd `x-access-token:*** URL. Before relying on the
env, check its protection rules (`gh api repos/<owner>/<repo>/environments`)
    - required reviewers or a wait timer stall the tag-push automation.
- **Fine-grained PATs cannot be minted from the CLI with an
  OAuth-authenticated `gh` (`gho_` token): `POST /user/pat` returns 404
  unless the authenticating token carries the `pat:write` scope - which
  only a CLASSIC PAT can hold, and classic PATs have no creation API at
  all.** PAT creation is a one-time web-UI step (Settings → Developer
  settings → Fine-grained tokens; repo access = ONLY the child repo,
  Contents: write); the CLI handles everything after it - storage
  (`gh secret set <NAME> --env <Env>`), wiring. Probe the API once, then
  hand the web step to the user; do not loop on it.
- **A `Bump-Plugin-Gitlink`-style job gated on
  `if: startsWith(github.ref, 'refs/tags/Aphrodite/')` runs ONLY on tag-push
  refs - a manual `gh workflow run ... --ref Development` dispatch silently
  SKIPS it (conclusion: skipped), leaving the parent gitlink stale after a
  manual child push.** On tag pushes it runs after the publish jobs (their
  publish STEPS skip on the gated condition but the jobs still conclude
  success, satisfying `needs:`). Bump the gitlink manually when dispatching
  from a branch ref.
- **Submodule remotes in PlayForm repos are named `Source`, not `origin` -
  `git push origin` from inside a submodule fails with an SSH
  access-rights error.** Push `git push Source Current` (the .gitmodules
  `remote = Source` binding). The failure message looks like an auth
  problem; it is a missing-remote-name problem.
- **Scripts that run the repo's own freshly-built binary must resolve the
  explicit override (e.g. `APHRODITE_BIN`) BEFORE the PATH lookup - a
  stale cargo-installed copy on PATH shadows the fresh build and silently
  regenerates with the OLD behavior.** Resolution order: explicit override
  first, PATH fallback second, loud error + exit 1 when neither exists.
- **A generator that CREATES a new fixture file must extend the CI fixture
  validator's known-name branches (name prefix → required keys) in the SAME
  change.** The validator fails unknown names ("unexpected fixture name"),
  so the first CI run after the generator ships goes red on the new file
  (the generated `plugin_defaults.json` failed exactly this way). Add the
  prefix branch + required keys to the workflow, and run the validator's
  logic locally against the fixtures before pushing.
- **After a release push, "all good?" includes the branch's CI runs - check
  `gh run list` and triage failures into yours vs pre-existing.** Release
  assets and crates.io can be green while Check.yml is red on Development:
  new generated fixtures and workflow edits are yours to fix now; environment
  gaps (e.g. a pytest job whose plugin tests need a source tree the runner
  lacks) may be pre-existing - verify with the workflow's run history
  (same failure before the release commit) before blaming or fixing it.
- `cargo test` on this fleet's codegen'd doc examples fails as doctests
  (`crate::` paths, bare `Fn`/`Option`) - scope the publish Test gate to
  `cargo test --release --tests --bins`; the unit harnesses still run.
- **The fmt gate is the PINNED NIGHTLY rustfmt, never the toolchain's
  stable one.** A rustfmt.toml with `unstable_features = true` plus
  nightly-only options (`space_after_colon`, `imports_granularity`,
  `group_imports`, doc-comment formatting, the `ignore` list) is SILENTLY
  IGNORED by stable rustfmt - it warns and skips, emitting space-after-colon
  / flat-import output that diverges from CI. `cargo fmt` resolves the
  toolchain from rust-toolchain.toml (usually stable), so the gate-equal
  formatter is `cargo +nightly-<pin> fmt`; verify with
  `cargo +nightly-<pin> fmt --check`, NEVER plain `cargo fmt --check` (a
  green stable check proves nothing). Running the stable formatter can
  itself REINTRODUCE the divergence the nightly gate then fails. VSCode
  Alt+F diverges the same way unless rust-analyzer is overridden to the
  nightly (`rust-analyzer.rustfmt.overrideCommand` =
  `["rustup", "run", "nightly-<pin>", "rustfmt"]`). Scope format checks
  to the FULL workspace - `cargo fmt --check -p <crate>` covers only that
  crate and misses sibling crates' drift (a release gate must run the
  whole-workspace nightly check).
- **Mirror the CI job's exact scope when verifying format/lint gates.** A
  root-wide check with a NEWER tool version flags out-of-scope files and
  looks like a regression: latest ruff formats Python fenced blocks inside
  `.md`, so `ruff format --check .` lights up repo docs AND vendored
  submodule wiki files that the CI gate (scoped to a subdir) never touches.
  Verify with the CI's scope (`git ls-files '*.py'` never sees submodule
  content - use it, or the workflow's `src:` path) and the CI's pinned tool
  version before treating flags as real drift; a scoped green + a root-wide
  red is a scope mismatch, not a regression.
