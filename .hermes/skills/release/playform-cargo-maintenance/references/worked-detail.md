# PlayForm Cargo Maintenance - Worked Detail

Moved bulk for `playform-cargo-maintenance` SKILL.md (compression pass). One-line rules live in SKILL.md; full recipes, worked instances, probes, and the classification matrix live here.

## Lockstep extras + version-hit classification (Procedure step 1)

Multi-crate extras: the plugin submodule's `plugin.yaml` + `BINARY_VERSION`, version fixtures (`fixtures/<crate>_version.json`), and README badges in BOTH repos (root + plugin submodule).

After editing, grep the tree for the old version and classify each hit: version-of-record moves, INCLUDING workflow comments that name the dep-pin version (e.g. Publish.yml prose describing the path-dep) - left stale they describe a pin that no longer exists. Contracts (`minimum_hermes_plugin_version`), historical CHANGELOG entries, and generated docs (regenerated by CI to scratch, not diffed) do NOT move.

## Installed plugin tree byte-consistency (Procedure step 3)

The standing convention is that locally developed packages stay installed from the local dev checkout, never replaced by crates.io versions. The workspace root Cargo.toml is a virtual manifest, so point at the crate dir (`cargo install --path crates/aphrodite --force`). When the plugin locates the binary at a managed path, refresh THAT copy too. When the repo ships a plugin that must stay byte-consistent with the binary, re-sync the WHOLE installed plugin tree, not just the binary:

    rsync -a --exclude='.git' --exclude='__pycache__' plugins/aphrodite/ ~/.hermes/plugins/aphrodite/

Copying only the binaries leaves the installed copy's `BINARY_VERSION` / `plugin.yaml` stale, and the version handshake then reports binary X vs installed pin Y. Verify all four agree afterwards: `aphrodite --version`, the dylib version report, `plugin.yaml` `version`, and `BINARY_VERSION`.

## Submodule-checkout pitfall anatomy (Build.yml Finalize, v0.0.3)

A job that WRITES INTO a submodule needs its own `actions/checkout` with `submodules: recursive`. A release job that previously only hit the network (asset verification, release notes) has no checkout, and adding a step that writes `plugins/aphrodite/SHA256SUMS.txt` fails with "No such file or directory" at the first redirect (the v0.0.3 Build.yml Finalize job failed exactly this way).

When the release already exists, do NOT move the tag to re-run - complete the missing artifact manually: assemble the in-tree checksum file from the release's per-target sums with the BINARY_VERSION header, commit + push it in the child, bump the parent gitlink, and let the workflow fix ride for future releases.

## Cross-repo child push: PAT + extraheader recipe

Cross-repo child pushes from a workflow need a PAT, AND the persisted GITHUB_TOKEN extraheader must be removed GLOBALLY (or overridden per-command) or the push silently 403s as `github-actions[bot]` even with a valid PAT in the URL. actions/checkout sets `http.https://github.com/.extraheader` in the GLOBAL config; a child-local `git config --unset-all` does not reach it.

Working recipe:
1. Store a fine-grained PAT (contents:write on the CHILD repo only) as a secret on the Release ENVIRONMENT: `gh secret set NAME --env Release` (the job needs `environment: Release`).
2. `git -C "$CHILD" config --global --unset-all http.https://github.com/.extraheader || true`
3. Push: `git -C "$CHILD" -c http.https://github.com/.extraheader= push "https://x-access-token:*** Current`

## Gitlink-bump race: wait loop

A gitlink-bump job that runs on the tag push RACES the release workflow's Finalize child push - the Bump job must WAIT for the child tip whose in-tree SHA256SUMS.txt pins the release version, not just fetch once. The Publish workflow starts the same instant as the Build matrix; its Bump job completes minutes before Finalize pushes the checksum commit, so it always sees the pre-checksum child tip and exits "nothing to bump", leaving the parent gitlink stale by one child commit after every release.

Fixed loop: fetch origin Current, then `git show origin/Current:SHA256SUMS.txt | grep -q "^BINARY_VERSION: ${V}$"` (bounded, e.g. 40 x 15s), error out if it never appears. A 5x10s fetch retry is NOT enough - it only rides out a transient fetch failure.

## Child-repo push job: PAT scoping + guards

A workflow job that PUSHES into a submodule's own repo cannot use `GITHUB_TOKEN` - it is scoped to the parent repo and 403s on any other repo (public or private). The Finalize job that commits the in-tree `SHA256SUMS.txt` inside the child checkout must push to `<owner>/<child>`, so it needs a fine-grained PAT scoped to the CHILD repo only (Contents: write).

- Store it as an ENVIRONMENT secret (`gh secret set <NAME> --env <Env>` - repo-wide is unnecessary exposure); declare `environment: <Env>` on the job (environment secrets reach only jobs that declare the environment).
- Push via the token URL: `git -C "$CHILD" push "https://x-access-token:*** Current`.
- Guard the step with a loud `::error::` + exit 1 when the secret is empty - never push an unauth'd `x-access-token:*** URL.
- Before relying on the env, check its protection rules (`gh api repos/<owner>/<repo>/environments`) - required reviewers or a wait timer stall the tag-push automation.

## Fine-grained PAT minting (web-UI only)

Fine-grained PATs cannot be minted from the CLI with an OAuth-authenticated `gh` (`gho_` token): `POST /user/pat` returns 404 unless the authenticating token carries the `pat:write` scope - which only a CLASSIC PAT can hold, and classic PATs have no creation API at all.

PAT creation is a one-time web-UI step (Settings → Developer settings → Fine-grained tokens; repo access = ONLY the child repo, Contents: write); the CLI handles everything after it (storage `gh secret set <NAME> --env <Env>`, wiring). Probe the API once, then hand the web step to the user; do not loop on it.

## Fixture-generator validator coupling (worked instance: plugin_defaults.json)

A generator that CREATES a new fixture file must extend the CI fixture validator's known-name branches (name prefix → required keys) in the SAME change. The validator fails unknown names ("unexpected fixture name"), so the first CI run after the generator ships goes red on the new file (the generated `plugin_defaults.json` failed exactly this way). Add the prefix branch + required keys to the workflow, and run the validator's logic locally against the fixtures before pushing.

## Nightly rustfmt gate (full detail)

The fmt gate is the PINNED NIGHTLY rustfmt, never the toolchain's stable one. A rustfmt.toml with `unstable_features = true` plus nightly-only options (`space_after_colon`, `imports_granularity`, `group_imports`, doc-comment formatting, the `ignore` list) is SILENTLY IGNORED by stable rustfmt - it warns and skips, emitting space-after-colon / flat-import output that diverges from CI.

- `cargo fmt` resolves the toolchain from rust-toolchain.toml (usually stable), so the gate-equal formatter is `cargo +nightly-<pin> fmt`; verify with `cargo +nightly-<pin> fmt --check`, NEVER plain `cargo fmt --check` (a green stable check proves nothing).
- Running the stable formatter can itself REINTRODUCE the divergence the nightly gate then fails.
- VSCode Alt+F diverges the same way unless rust-analyzer is overridden to the nightly (`rust-analyzer.rustfmt.overrideCommand` = `["rustup", "run", "nightly-<pin>", "rustfmt"]`).
- Scope format checks to the FULL workspace - `cargo fmt --check -p <crate>` covers only that crate and misses sibling crates' drift (a release gate must run the whole-workspace nightly check).

## Gate-scope mirroring (worked instance: ruff / .md)

Mirror the CI job's exact scope when verifying format/lint gates. A root-wide check with a NEWER tool version flags out-of-scope files and looks like a regression: latest ruff formats Python fenced blocks inside `.md`, so `ruff format --check .` lights up repo docs AND vendored submodule wiki files that the CI gate (scoped to a subdir) never touches.

Verify with the CI's scope (`git ls-files '*.py'` never sees submodule content - use it, or the workflow's `src:` path) and the CI's pinned tool version before treating flags as real drift; a scoped green + a root-wide red is a scope mismatch, not a regression.
