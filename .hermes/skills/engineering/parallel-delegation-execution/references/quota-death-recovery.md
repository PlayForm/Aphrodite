# Provider quota deaths and recovery

- **Relaunch a failed child - never hand-execute its scope mid-wave (standing orchestration preference).** When a child dies (401/429/timeout), re-dispatch it instead of writing its files yourself: the parent organizes and verifies, children implement. This governs scope a child already OWNS mid-wave; it does not repeal "finish the sweep directly", which governs the final integration pass after the waves land.

- **Provider per-minute inference quota caps parallel fan-out: 429s mean the wave is too wide - re-dispatch failed units SEQUENTIALLY.** A 4-way parallel batch can kill 2-3 children with HTTP 429 "rate limiting: inference request per min rate reached" within ~50s; the runtime cap is not the binding constraint, the provider's per-minute quota is. Let the surviving children finish, then re-dispatch the failed units one at a time or in a 2-wide wave - never re-fan-out the ORIGINAL width. An INSTANT death (sub-second, 429 or 401 at or near the first model call) has produced NOTHING - re-dispatch; a LATE death (long runtime, died composing the final summary) has USUALLY landed the full deliverable - the batch reports it "failed" but the on-disk evidence confirms it, so do NOT re-dispatch: a re-run burns a full quota window. An instant 401 (auth) death on the Cloudflare Workers AI provider is a TRANSIENT blip: solo re-dispatch succeeds - re-dispatch the moment the per-task early-warning arrives, never wait for the batch-complete message, never report hard-broken provider auth. After a MIXED 429+401 cluster, probe with ONE minimal agent before re-fanning out - the failure window can outlast the batch; re-fan 2-wide only after the probe completes. A child that died with partial results in the transcript still counts - re-dispatch only the undelivered items.
