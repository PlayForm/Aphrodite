# Scar catalog (test cases)

1. **Parent establishes the repro baseline itself first** (cheap checks: run the failing test, stage the shallow path, trace the claimed code path) - and for pasted inspection/fix ledgers verifies each claim's DIRECTION, not just its existence: push_front means index 0 is newest, so .iter().rev() reaches the OLDEST entries - a 'cosmetic ordering' fix misreported old entries as new. Grep the test suite for tests that LOCK current behavior before dispatching any behavioral 'improvement' (record-time adaptation and cap-eviction arithmetic were both asserted as intended by existing tests and had to be retracted). When a fix names a dependency, grep the workspace Cargo.toml and lockfile first - the dep is often already enabled with an in-repo usage pattern to copy (an lru-cache fix needed no new dependency; the crate was already default-enabled with precedent in the proxy).

- **The external auto-committer is a standing third writer.** It may sweep session work into commits behind your back (author = the account's git identity, mid-session timestamps, working tree suddenly clean) without any child running git. Warn children in their task context: "do NOT run git commit; an external auto-commit may run - ignore it". When verifying, check `git log --oneline -5` + `git status` first; if auto-commits appeared, report them to the user rather than silently `git reset`-ing - the content is legitimate session work; fighting the auto-committer is a losing loop. The session-start workspace snapshot goes stale by planning time for the same reason: a wave scoped from the prompt snapshot mis-owns files that are no longer working-tree changes - the planning baseline is the tree at brief-writing time, never the snapshot (re-run `git status` + `git log --oneline -5` before naming owned files).
