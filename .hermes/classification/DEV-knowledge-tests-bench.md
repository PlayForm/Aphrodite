1. **Dev knowledge never reaches Current - and the ceremony enforces it twice.** `.hermes/**` (incl. `skills/`, `uml/`, `release/`, `release-notes/`, `classification/`) and `bench/**` are in the Phase A protected restore (`Action 10: git checkout HEAD -- … .hermes bench`) AND the Phase B Development-identity restore (`Action 7`), and RELEASE-SCOPE's DEV-INFRA table names them explicitly. The one thing dev-knowledge _does_ cross is its influence: RELEASE-METHODOLOGY + RELEASE-STRATEGY + the branch-release-flow skill drive the ceremony itself, and `Maintain/release-notes-vX.Y.Z.md` (the ritual doc, `D@R4-01 →C +tag`) is _authored_ from `.hermes/release/RELEASE-TEMPLATE.md` + `.hermes/release-notes/*-draft.md`.

2. **Release-notes staging is a two-line ritual with one crossing artifact.** Draft lives Dev-side (`.hermes/release-notes/v1.4.3-draft.md` → archived as `.hermes/release-notes/v1.4.3.md` after the 1.4.3 tag shipped; `DD6-16 ∅ @A`), the _finalized_ note that crosses is the `Maintain/` copy (`D@R4-01 →C +tag`, owned by the release-infra pass), and `gh release --notes-file` consumes it. The `.hermes/release-notes/v1.4.0-1.4.6.md` files are post-hoc **archives** of shipped notes (`@A` - amendment below) - they document the Tag composition after the fact but never participate in it. Drafts of future releases (`v1.5.0-draft.md` per strategy §7.3) follow the same staging path.

3. **Development KEEPS tests in Phase B - the asymmetry is structural.** Current deleted all tests (`966cb41` test-free policy) and removed the `Test` job from `Check.yml` (`3589b33`). So `TD6-*` files have a _negative_ ceremony behavior: they are re-protected against the upward flow.

## 3. Cross-cutting observations

- **The dev-side scope is a one-way knowledge sink.** Everything here is `D*6 ∅` except `docs/**` (`DB6 →C`) and `assets/**` (`AB6 →C`). Knowledge flows _down_ freely (Development accumulates append-only: notes, skills, UML, bench) and _up_ only as finished content (docs). The taxonomy captures this asymmetry exactly: layer 6 is where "which process feeds which process" is mostly one-directional - the processes that _produce_ the release (methodology, strategy, handoff, scope, skills) never ride the artifact they produce.
- **Every `.hermes/notes/session/CONTINUE-*` file is a literal halted process.** They open with "Read this FIRST to resume" and carry state tables, next-steps in order, and known-issues - the strongest confirmation of the taxonomy's core framing. `RELEASE-METHODOLOGY.md` is the permanent continuation; the CONTINUE notes are the session-scoped ones. Same pattern at skill granularity: `aphrodite-branch-release-flow` is the ceremony-as-procedure, `aphrodite-release-workflow` is its predecessor (superseded by the methodology, kept as history).
- **Resume = run for `S*6`/`P*6`, re-hydrate for `D*6`.** Scripts (`build-watcher`, `mock_upstream`, `harness`, `bench_proxy`, `gen_corpus`, `verify_labels`) _start processes_ when opened/executed; docs and notes _restore process state in the reader_. The taxonomy's halt/resume semantics map onto this split cleanly.
- **Tests anchor Dev-only mechanisms that the docs describe to Current.** `tests/test_directives_materialize.py` verifies the mechanism `DIRECTIVES-RELOCATION.md` specifies; `test_layout_check.py` verifies the spec in `LAYOUT-SELF-HEAL.md`; `test_hotreload.py` verifies the plugin shim `uml/08` traces. The knowledge layer and the test gate are the same process seen from two sides - one ships its docs, the other never ships at all.
- **Layer-by-location, not by function.** `.hermes/release/*` and `release-notes/*` are functionally layer 4 (release infra) but sit in `.hermes` → layer 6. The taxonomy's layer map says `.hermes/` = 6, so classification follows location; the functional layer-4 adjacency (RELEASE-SCOPE as `MD6-01 +guard` behaves like a release manifest) is worth a taxonomy note (amendment 2).
- **Untracked ≠ unprotected.** `.hermes/classification/` is untracked (`??`) - the squash transplant only stages _tracked_ changes, so untracked dev scaffolding would not even reach the staged set; and if committed, the protected-path restore drops it anyway. Two independent layers of protection.
