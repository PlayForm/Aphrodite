## 2. Notable ceremony interactions

1. **The tag trigger chain (the commutative heart of the Tag):**
   `D:{auto-release.sh}` → bumps `+bump` versions + writes `plugins/aphrodite/BINARY_VERSION` + tags plugin `vX.Y.Z` (submodule) + tags parent `Aphrodite/vX.Y.Z` → Phase A transplant (A1 plugin squash → A2 parent squash → A10 identity restore → A11 gitlink float → A13 commit/tag/gh release) → tag `refs/tags/Aphrodite/v*` fires `Build.yml` (creates release once, 12 assets, Finalize asserts) AND `Publish.yml` (crates.io, see discrepancy below). Consumers on the user side: `download.sh`/`setup.rs` resolve the binary by `BINARY_VERSION` → `releases/download/Aphrodite%2Fv{V}` - **they only work if Build.yml produced identically-named assets** (`aphrodite-{target}`, `libaphrodite_hermes-{target}`, `SHA256SUMS-{target}` for all 4 targets). BINARY_VERSION is bumped LAST (MC3-01 +tag, rule 2) precisely so the pointer never precedes the assets.
2. **Artifact contract (Build.yml ↔ download.sh/setup.rs):** staging renames to platform-suffixed names with `fail_on_unmatched_files: true`; Windows checksums use pwsh (the MSYS `findstr` path-mangling incident); Finalize runs `gh release view` and fails loudly if any of the 12 assets is missing - release notes can never claim an incomplete platform set (the "no Windows release" race-killer). The v1.4.3 notes' "What Ships" table is the human mirror of this contract.
3. **Identity restoration at EVERY transplant (the ∅ discipline):** Phase A Action 10 restores `HEAD -- .gitmodules .github/workflows plugins/aphrodite .hermes bench`; Phase B Action 7 restores `.gitmodules .github/workflows plugins/aphrodite vendor/headroom`. I9 verifies `git diff HEAD -- .gitmodules .github/workflows .hermes bench` is EMPTY after staging. The G5-* ∅ set (branch-variant triggers + per-branch branch fields) is what makes the two lines genuinely "two products": Development's Check.yml runs the Test job, Current's doesn't; Development's plugin gitlink floats to Development tip, Current's to Current tip. **The hooks (SB5-01..06) are the mechanical enforcers of this - identity is kept consistent by pre-commit's behind-tip refusal and post-checkout's tracking-branch force, not by ceremony discipline alone.**
4. **Release-notes ritual @R staging:** notes are finalized at `Maintain/release-notes-v1.4.3.md` on Development (A0), consumed ONCE by `gh release create --notes-file` (Action 13, never inline backticks), and picked back up in Phase B (B3 transfers "finalized release notes"). `release-notes.sh` generates the compare header scoped to `Aphrodite/v*`. The notes must be authored AFTER Build.yml Finalize confirms the matrix (the race-killer) - the doc and the workflow are mutually asserting.
5. **Auto-committer handling (three distinct processes):** (a) CI-side `Auto.yml` - daily heartbeat commits `.github/Update.md` and pushes **Current** (accepted I10 exception; path is `paths-ignore`d in Check.yml and `export-ignore`d in .gitattributes); (b) the SANCTIONED local hooks - post-commit/post-checkout auto-commit gitlink bumps, post-merge auto-commits pin floats (pathspec-scoped, never sweeping other staged work); (c) the UNSANCTIONED local sweeper (Part 6) - can stage a **phantom self-referential gitlink** (160000 entry named after the submodule pointing at its own HEAD, no dir on disk; symptom `A plugins/aphrodite`/`AD vendor/headroom`) - never fight it: `git rm --cached <path>` inside the submodule, verify `git ls-files -s` shows no 160000, and verify with `git log` (it may commit mid-review staged sets).
6. **Publish.yml vs methodology discrepancy (flagged):** Part 4 says crates.io needs manual `publish_crates:true` - true only for `aphrodite-headroom-core`; the `aphrodite` and `aphrodite-hermes` publish steps are gated `(dispatch && publish_crates) || refs/tags/Aphrodite/*` and WILL fire on a plain tag push (failing loudly if headroom-core isn't already live). The workflow is looser than the doc; advanced methodology should reconcile (either tighten the workflow condition or update the doc).
7. **The plugin moves first (bottom-up) everywhere:** A1 plugin sync before A2 parent; B1 plugin sync-back before B2; `auto-release.sh` commits/tags/pushes the plugin submodule BEFORE tagging the parent; post-commit keeps the parent gitlink at the submodule tip so the float in A11 is a formality. `submodule first, always` (rule 1) is enforced across scripts, hooks, and docs simultaneously.

## 3. Cross-cutting observations

(for the advanced methodology)

- **Hooks are the identity machinery, not the docs.** The ∅ rules in RELEASE-METHODOLOGY are enforced _mechanically_ by SB5-01 (behind-tip refusal), SB5-03 (detached-HEAD refusal → force tracking branch), SB5-02/04 (auto-bump/floats). The ceremony is now largely self-maintaining; what's left to human discipline is the transplant staging (A4/A9/A10 selective picks) and the tags.
- **The vendor pin is NOT line-variant; the plugin gitlink IS.** `.gitmodules` on Development: plugin `branch = Development`, vendors `branch = Current` - so "branch field per-branch" (G5-01 ∅) refines to "the plugin's branch field is per-branch; vendor fields are line-fixed to Current". Vendors float to Current tip on both lines, which is why Phase B Action 7 restores `vendor/headroom` (its pin is Current-line-owned) while the plugin gitlink is re-floated per line.
- **Two enforcement layers for "dev scaffolding never ships":** transplant-level (A10 restores `.hermes bench` out of Current) AND artifact-level (.gitattributes `export-ignore` for `.hermes`/`.github` in source zips; .dockerignore/.npmignore for container/npm surfaces). .gitignore's `!.hermes/` re-include keeps the dev archive tracked on Development - the track-vs-ship split is deliberate and orthogonal.
- **The artifact contract is a three-way assertion:** Build.yml Finalize (assets present) ↔ release-notes "What Ships" table (claims only verified assets) ↔ download.sh/setup.rs (BINARY_VERSION → URL → asset names). Break one and users get 404s or wrong-platform binaries (TD4-05 is the frozen narrative of exactly this failure class).
- **Stale references to deleted processes:** Format.sh exclusion rules, .gitignore's empty "Profiles" section, and likely docs still mention `profiles/` and `Maintain/install.*` - cleanup candidates (docs-consistency-oneshot.sh is the tool for it). Their absence is a rule, but the mentions are drift.
- **Adjacent files observed (NOT in this scope, verify ownership with the other passes):** `.github/dependabot.yml` (root-level dependabot config), `.github/FUNDING.yml`, `.github/Update.md` (Auto.yml write target), `.gitguardian.yaml` (ggshield config consumed by pre-commit), `.github/workflows/` only - Dependabot.yml/GitHub.yml classified above as shared; `.editorconfig` (shfmt source).
- **auto-release.sh vs methodology tension:** the script (SD4-01) can push tags and commit on whatever branch it's started on (`RELEASE_BRANCH` from HEAD) - methodology I10 wants Current touched only inside the ceremony window and tags only at the END. The script is Development-prep tooling; treat its tag/push steps as the ceremony's mechanical part, keep the human sequencing (A0 preconditions, A4 selective pick) intact.
- **Commutative diagram (who feeds whom at ceremony time):**
    ```
    D:{auto-release.sh} ──bumps──▶ D:{Cargo.toml, package.json, README badge}  D:{BINARY_VERSION in plugin tree}
          │                                  │                                        │ (bumped LAST)
          │                                  ▼                                        ▼
          │                         Phase A: D:{tree} --merge --squash--> C:{tree}   ┌──┐
          │                                  │ A10 restore G5-* ∅                     │  │ download.sh/setup.rs
          │                                  ▼                                        ▼  │
          └── tag ──▶ C:{Aphrodite/vX.Y.Z} ──fires──▶ C:{Build.yml} → 12 assets ──▶ releases/ ──▶ (BINARY_VERSION lookup)
                                                        C:{Publish.yml} → crates.io (headroom-core → aphrodite → aphrodite-hermes)
          C:{release-notes-v1.4.3.md} ──gh release create --notes-file──▶ Tag body
          C:{hotfix} ──cherry-pick -x──▶ D:{hotfix}   (Phase B, upward only)
          C:{fixes} ──Phase B squash + B7 identity restore──▶ D:{fixes}
          S:{post-commit/post-merge hooks} ──auto-bump/floats──▶ G5-01 gitlink (stays branch-owned, never crosses)
    ```
    Identity (G5-* ∅) and dev scaffolding (SD4-_/TD4-_/CD4-_/DD4-_, Procfile.dev, bench) never appear on the C side of the diagram.
