## 2. Notable ceremony interactions

1. **The tag trigger chain (the commutative heart of the Tag):** manual r1 (bumps `+bump` versions, writes `plugins/aphrodite/BINARY_VERSION` LAST) → Phase A transplant (A1 plugin squash → A2 parent squash → A10 identity restore → A11 gitlink float → A13 commit/tag/gh release) → tag `refs/tags/Aphrodite/v*` fires `Build.yml` (creates the release once, 12 assets, Finalize asserts) → Build.yml Finalize pushes the child SHA256SUMS commit to child Current via the PAT and **tags the plugin `vX.Y.Z` from the child tip** → `Publish.yml` chains off the successful Build run (`workflow_run`, tag-shaped head_branch): crates.io (`aphrodite` → `aphrodite-hermes`; the headroom-core publish step is unreachable dead code) → Bump-Plugin-Gitlink floats the parent gitlink onto the child tip (degrades with a warning when Current is branch-protected). Consumers on the user side: `download.sh`/`setup.rs` resolve the binary by `BINARY_VERSION` → `releases/download/Aphrodite%2Fv{V}` - **they only work if Build.yml produced identically-named assets** (`aphrodite-{target}`, `libaphrodite_hermes-{target}`, `SHA256SUMS-{target}` for all 4 targets). BINARY_VERSION is bumped LAST (MC3-01 +tag, rule 2) precisely so the pointer never precedes the assets. Note the tag ORDER inversion vs the auto-release.sh era: the PARENT tag now precedes the PLUGIN tag (the parent tag fires the chain that creates the child tag at the child tip).
   `D:{auto-release.sh}` → bumps `+bump` versions + writes `plugins/aphrodite/BINARY_VERSION` + tags plugin `vX.Y.Z` (submodule) + tags parent `Aphrodite/vX.Y.Z` → Phase A transplant (A1 plugin squash → A2 parent squash → A10 identity restore → A11 gitlink float → A13 commit/tag/gh release) → tag `refs/tags/Aphrodite/v*` fires `Build.yml` (creates release once, 12 assets, Finalize asserts) AND `Publish.yml` (crates.io, see discrepancy below). Consumers on the user side: `download.sh`/`setup.rs` resolve the binary by `BINARY_VERSION` → `releases/download/Aphrodite%2Fv{V}` - **they only work if Build.yml produced identically-named assets** (`aphrodite-{target}`, `libaphrodite_hermes-{target}`, `SHA256SUMS-{target}` for all 4 targets). BINARY_VERSION is bumped LAST (MC3-01 +tag, rule 2) precisely so the pointer never precedes the assets.
2. **Artifact contract (Build.yml ↔ download.sh/setup.rs):** staging renames to platform-suffixed names with `fail_on_unmatched_files: true`; Windows checksums use pwsh (the MSYS `findstr` path-mangling incident); Finalize runs `gh release view` and fails loudly if any of the 12 assets is missing - release notes can never claim an incomplete platform set (the "no Windows release" race-killer). The v1.4.3 notes' "What Ships" table is the human mirror of this contract.
