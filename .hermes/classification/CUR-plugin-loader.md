## 2. Notable ceremony interactions

1. **BINARY_VERSION last-bump rule** (`MC3-01 +tag+guard`): the manifest is a LIVE distribution pointer -
   both downloaders build `releases/download/Aphrodite%2Fv{V}` from it and `_check_version` handshakes it
   against the loaded dylib. Bumping it before the release assets exist breaks every download, so it is
   bumped LAST in any ceremony (after all code/config fixes, immediately before the tag). It also pairs
   **two independent release lines**: binary `Aphrodite/v1.6.4` vs plugin `v2.2.4` - the plugin's cadence
   and the binary's cadence are decoupled by design and this one file couples them.
2. **Submodule-first ordering (bottom-up)**: `plugins/aphrodite` syncs BEFORE the parent in BOTH directions -
   Phase A1 (plugin snapshot + commit + push) precedes A2 (parent), Phase B1 precedes B2. The parent gitlink
   must reference the plugin's tip, so the plugin is always the first process resumed and the last settled.
3. **Plugin gitlink float** (`+float`): the parent's 160000 gitlink entry for the submodule is floated to the
   released plugin tip at Action 11 (currently `895892a` on Development; floated via `a639138`, preceded by `6102c1c` via `a9f22f1`). The gitlink is
   branch-owned identity (restored per branch at Action 10/7) - the submodule's own tree is shared content;
   the pointer that floats is parent-side and owned by the release-infra/identity partner.
4. **plugin.yaml version rides the release** (`MB3-01 +bump +tag`): plugin tag `v2.2.4` exists (`0caf55f` on S-Current); the manifest
   version is bumped on Development pre-A0, carried in the A1 squash snapshot, and the plugin is tagged FIRST
   (`v2.2.4` on S-Current, then `Aphrodite/v1.6.4` on P-Current). The plugin has NO CI of its own - the tag
   is its release marker.
5. **Template drift guard** (`+guard`, verified live): `crates/aphrodite/templates/__init__.py` is
   **byte-identical** to this `__init__.py` (wc -c verified, 54470 B both sides, 2026-09-26). The embed moved with the
   setup.rs → `setup/` dir-module atomization: `crates/aphrodite/src/setup/write.rs:85` `include_str!("../../templates/__init__.py")`
   and the drift-guard test lives at `crates/aphrodite/src/setup/tests.rs:50` (`test_hermes_plugin_shim_template_matches_live`);
   the templates dir also holds `aphrodite.toml` (`CONFIG_TEMPLATE`, write.rs:9).
   Ceremony rule: format the PLUGIN first, then `cp` to the template - the plugin copy is the source of truth;
   `ruff.toml`/`rustfmt.toml` ignore the templates dir for the same reason. The template is the crate's
   embedded copy of the loader (TAXONOMY `MB1-05 +guard`).
6. **skills/directives NOT shipped** (deliberate absence rules): skills live dev-side in `.hermes/skills/`
   (Development-only, never on Current); directives moved into the binary's `builtin_directives` and are
   materialized to the user-data home at startup. Both keep the plugin a pure loader - nothing in the
   submodule carries agent-behavior content across the boundary.
7. **Layout check is the runtime mirror of the ceremony**: `layout_check.py` + `layout_schema.json`
   enforce "plugin dir = pure loader" on the user side by **reporting** deviations (forbidden: `binaries/`, `aphrodite.toml`, `ccr.db`
   in the plugin dir; forbidden: plugin-source files in the runtime home) - report-only, never moves anything - the same separation the release
   ceremony enforces on the git side. A dev checkout is detected and left alone (developers manage the
   checkout), which is exactly the Development-vs-Current split made operational.
8. **Downloader guard around the last-bump pointer**: both downloaders run a strict semver regex
   (`^[0-9]+\.[0-9]+\.[0-9]+([-.][0-9A-Za-z.]+)?$`) that rejects a malformed BINARY_VERSION (e.g. a stray
   `1|1.3.9` line-number artifact) before a bad release URL can be built - the plugin's own defense-in-depth
   around rule #1. `__init__._ensure_binaries` pins `BINARY_DIR` explicitly so an ambient env var can't
