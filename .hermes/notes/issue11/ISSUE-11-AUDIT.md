## (c) Hook path reality check

- **Call sites:** `transform_tool_result` (lib.rs:414) and `transform_terminal_output` (lib.rs:435) both call `crate::tools::unwrap_hermes_result`; the result feeds the `classify: Option<(&str,&str)>` param of core `transform_tool_result_inner`/`transform_terminal_output_inner` (hooks.rs:172-197, 375-400). Core hashes/stores the ORIGINAL `content` (hooks.rs:193-195) and uses classify only for `type_str` + `build_preview` (hooks.rs:197). Storage lossless on the hook path too.
- **Real Hermes envelopes** (verified live this session + pinned by lib.rs:852-890 test): terminal → `{"output":...,"exit_code":N,"error":null}`; search_files → `{"total_count":N,"matches":[...],...}`; read_file → `{"content":...,"total_lines":N,...}`; patch/write_file → `{"success":...,"diff":...,"error":...}`. **The unwrap IS genuinely needed on the hook path** - without it, every automatic compression of a terminal/search/read result would preview as `[json:...]` (design pinned by `test_call_hook_transform_tool_result_unwraps_hermes_wrapper`, lib.rs:847-890, and tools.rs:654-667 terminal type test).
- **What would happen if explicit `aphrodite_compress` did NOT unwrap:** the caller's hint would be honored (tools.rs:197), JSON payloads would classify as json-family with a full-content preview (`[json:2keys 1L | success, data]` with hint → `[tool_result:1L 47B | {"success":true,...}]`), and the hook path would be untouched (separate call sites). The only loss: storing a literal Hermes wrapper string via `aphrodite_compress` would get a plain JSON preview instead of a terminal one - an acceptable trade, and the `type` hint covers it. **Conclusion: unwrap on the explicit path is unnecessary and is the bug; the heuristic belongs to the hook path only.**
- **Hook path has the same false-positive class** (ROOT-CAUSE §5.1): any tool result that happens to match a wrapper shape - `{"result":"ok",...}`, `{"content":"..."}`, `{"success":true}`, `{"total_count":N}` - gets its type/preview rewritten with no hint to disambiguate. Same 9-shape table applies; damage is type/preview-only there too.

## (d) detect_type / build_preview / dead-config findings

- **detect_type** (preview.rs:14-19) is a thin wrapper over the vendored Headroom classifier (`transforms::content_detector::detect_content_type`). JSON content classifies as a json-family type (`json`/`json_array`; proxy test proxy.rs:2977 pins `[{"a":1},...]` → `"json"`). **There is NO distinct `json_object` type in the taxonomy** - build_preview's json arm (preview.rs:273) covers `json_array | json | json_list` and `build_json_preview` (preview.rs:574-607) renders objects as `[json:Nkeys NL | k1, k2, …]` via its `Object` arm. So a JSON payload, if it ever reached the classifier, would get an honest `[json:2keys 1L | success, data]` preview.
- **Why the reported payload classifies as `text`:** the classifier never sees it. `unwrap_hermes_result` collapses `{"success":true,...}` (≤2 keys) to the fragment `"ok"` with type `"text"` (tools.rs:123-126); `compress_into` then uses that type verbatim (tools.rs:193-194), silently discarding the caller's `tool_result` hint (hint is only consulted in the else-branch, tools.rs:196-198).
- **How `1L 2B` is computed:** `build_preview("text", "ok")` (preview.rs:169-307): `lines = content.lines().count()` = 1; `bytes = content.len()` = 2; `effective` stays `text` (`detect_semantic_type("ok")` → None, preview.rs:178-181); generic `_` arm (preview.rs:294-304) renders `[text:1L 2B | ok]`. The line/byte counts and hint are computed from the FRAGMENT, not the stored payload - the marker's `size` field (original content) stays honest while the preview lies.
- **Dead config levers - CONFIRMED:** `model_family` (config.rs:256) and `preview_max_chars` (config.rs:258) are declared in `PreviewsConfig`, and those two lines are the ONLY occurrences in the whole crates tree - nothing reads them, and `PreviewsConfig` itself is never referenced outside config.rs. There is no preview-template/model-aware system; every preview funnels through `build_preview`. No config can change the outcome; both knobs are inert (also confirmed by the reporter's experience - issue #11 mentions trying config knobs to no effect).

## (e) Full bug class - every false-positive shape and its symptom

The heuristic cannot distinguish a Hermes envelope from a user JSON payload. On BOTH the explicit compress path and the hook path, any object matching a wrapper shape gets its type/preview rewritten:

| #   | false-positive input shape                                                                     | resulting type / preview (symptom)                                                                                                                       | source                                                                       |
| --- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 1   | **`success:true` + ≤2 keys**                                                                   | literal `"ok"`, type `text`, preview `[text:1L 2B \| ok]` - **the reported ISSUE-11 symptom**                                                            | tools.rs:123-126; test tools.rs:570 pins it                                  |
| 2   | **`success` string** (`"ok"`, `"wrote 3 files"`, …)                                            | collapses to that string, type `text`                                                                                                                    | tools.rs:127-131                                                             |
| 3   | **`result`/`message`/`description`/`summary`/`preview`/`found` string field, ANY object size** | collapses to that one string, type `text` - same "ok" symptom at any size                                                                                | tools.rs:167-174; no len guard                                               |
| 4   | **`content` string field**                                                                     | collapses to inner string, type = detect of fragment (usually `text`), e.g. `{"content":"hi","id":42}` → `[text:1L 2B \| hi]`                            | tools.rs:158-162; the 01-F2 test knowingly accepts the type/preview collapse |
| 5   | **`output` + `exit_code` pair**                                                                | inner fragment classified `terminal`/`build_output`/`build_error`/`text`; a legit API response with these keys is mislabeled and its extra fields hidden | tools.rs:81-107                                                              |
| 6   | **`total_count` (+`matches`) key**                                                             | type `search`, preview is fabricated grep lines (`path:line:content`) or bare "N total"; a data object with a `total_count` field becomes type `search`  | tools.rs:134-156                                                             |
| 7   | **`diff` string field**                                                                        | type from diff fragment, rest of object hidden                                                                                                           | tools.rs:110-114                                                             |
| 8   | **`error` string field** (non-JSON-starting)                                                   | only the message survives in type/preview, `code`/`retry_after`/other fields invisible                                                                   | tools.rs:115-122                                                             |

Common consequences across ALL shapes:

- **Caller hint discarded** on the explicit path (type flips to `text`/`search`/`terminal`/`build_*` even when the caller passed e.g. `type: "tool_result"`).
- **Preview lies about size/shape**: L/B counts and the hint come from the fragment, so `1L 2B` can be printed for a 737-byte payload; the model's retrieval decisions (catalog/search/`[preview]` glance) are fed wrong signals.
- **Storage/retrieval always lossless** (since e25aa85): hash/store use the original content on both paths; the marker's `size` field is honest - only `type` + `preview` are corrupted. This is why the issue manifests as "preview broken, content fine".
- **Type corruption also breaks `aphrodite_search` type filters and any type-based downstream logic** (search matches `mk.ccr_type`, tools.rs:345).
- Same class fires on the hook path for ANY tool whose result matches a shape, with no hint to disambiguate (no fix that only touches compress_into closes the hook-path variants; ROOT-CAUSE §5.1).

**Fix direction (from ISSUE-11-ROOT-CAUSE, not applied here):** on the explicit path, a caller hint must win over the heuristic and JSON previews must build from the full content; optionally drop/guard the `"ok"` collapse so it requires a known envelope key (`exit_code`/`total_count`/`matches`/`diff`) - since `output`/`exit_code`, `diff`, `error`, `total_count`/`matches`, `content` are all handled by branches above it, the success-bool branch only ever false-positives.
